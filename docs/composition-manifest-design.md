# Composition Manifest Design

**Status:** P0 contract for the manifest schema implemented in P1.9

**Version target:** manifest schema `0.3.0`

## Compatibility rule

Schema `0.3.0` is an additive tagged union over the existing curated manifest
shape. Existing generated manifests remain byte-for-byte unchanged and continue
to validate as the legacy curated branch. The generator does not start emitting
`run.kind` merely because the schema can represent it.

The run discriminator has three interpretations:

| `run.kind` | Meaning |
| --- | --- |
| absent | Legacy curated manifest emitted by existing `generate` behavior. |
| `curated` | Explicitly tagged curated manifest with the same registry semantics. |
| `composition` | Caller-authored composition manifest; requires the composition branch. |

An explicit curated branch cannot contain composition entries. A composition
branch cannot contain curated `case_id` file entries, registry profile coverage,
negative/fuzz qualifications, or curated `skipped_cases`.

## Top-level shape

The shared top-level provenance remains `generated_at`, `generator`,
`standards`, and `dependencies`. The `run` value selects one of these payloads:

```json
{
  "manifest_schema_version": "0.3.0",
  "generated_at": "20000101T000000Z",
  "generator": {},
  "standards": {},
  "dependencies": {},
  "run": {
    "kind": "composition",
    "seed": 1,
    "composition_spec_schema_version": "0.1.0",
    "input_spec_sha256": "<sha256>",
    "template_catalog_schema_version": "0.1.0",
    "template_catalog_sha256": "<sha256>"
  },
  "composition": {
    "entries": [],
    "assets": [],
    "unavailable_capabilities": [],
    "publication": {}
  }
}
```

Composition does not reuse `files[].case_id`. Its `entries` contain generated
instance records, and dependencies generated by a template bundle are ordinary
entries distinguished by `bundle_role` and `requested = false`.

## Composition run

The composition run block requires:

- `kind = "composition"`;
- deterministic `seed`;
- composition-spec schema version and exact canonical input-spec SHA-256;
- template-catalog schema version and exact catalog SHA-256;
- standards-lock SHA-256 through the shared standards block;
- deterministic resource-envelope values used for this run; and
- file-level parallelism requested and actually used.

Input-spec hashing occurs after JSON parsing and canonical key ordering but
before template default resolution. It includes caller-relative asset paths but
never a host absolute path. The original spec is not copied into the manifest
when it could contain large inline data; the exact hash and normalized redacted
projection are retained.

## Composition entry

Every resolved instance entry requires:

```text
instance_id
template_id
template_version
requested
bundle_root_instance_id
bundle_role
path
size_bytes
sha256
determinism
resolved_plan_sha256
dicom
uids
value_provenance
content
references
validation
standards_evidence
```

`instance_id` is caller-visible logical identity. Bundle dependencies receive a
deterministic logical suffix under the root instance. `template_id` and
`template_version` identify the exact qualified descriptor. No composition
entry has `case_id`, `profile_membership`, or a curated recipe block.

`value_provenance` is sorted by normalized tag and records exactly one origin:

- `template_default`;
- `run_default`;
- `instance_override`;
- `derived_structural`;
- `content_source`; or
- `provider`.

For derived values the record names the identity, reference, content-shape, or
Part 10 rule that supplied it. Protected collisions are rejected during
resolution and therefore never appear as competing origins.

## Assets and content

An asset is recorded once even when multiple slots consume it. Each asset
record requires:

```text
asset_id
spec_relative_path
kind
size_bytes
sha256
content_slots
staging_method
```

Only spec-relative paths are deterministic provenance. Private staging paths
and caller host paths are excluded. `content` records bind entry slots to asset
IDs or provider results and include exact frame, sample, document, mesh, or bulk
hashes appropriate to the slot. Encoded-frame entries also bind the declared
transfer syntax, fragment layout, decoder identity, and decoded semantic hashes
when qualification requires them.

Provider results additionally record provider protocol version, executable
fingerprint, argument-vector fingerprint, cleared-environment policy, request
SHA-256, response SHA-256, declared files, and observed resource outcome.

## Identity and references

The UID block retains Study, Series, SOP, Frame of Reference, and other
template-declared UID roles. Each reference records logical source and target
instance IDs, materialized SOP Class/Instance UIDs, relationship role, and
optional referenced frame numbers. The manifest assembler verifies that all
references close within the published entry set unless a template explicitly
permits an externally supplied UID reference.

The canonical resolved-plan hash covers normalized typed attributes, content
hashes and shape, materialized identities, references, transfer syntax,
template identity/version, standards lock, and determinism inputs. It excludes
output paths, staging paths, thread scheduling, and host environment.

## Validation evidence

Validation is an object with independent result groups:

- `part10`;
- `generic_data_elements`;
- `template`;
- `content`;
- `codec_or_provider`; and
- `independent`.

Each group records status, stable rule or adapter IDs, tool identity where
applicable, and findings. Allowed status values are `passed`, `failed`, and
`unavailable`. `unavailable` requires a stable reason code and cannot satisfy a
template's required qualification route.

The manifest is assembled from the same immutable resolved plan used by the
writer and generic validator. Expected structure is never reconstructed by
re-reading caller input after materialization.

## Unavailable capabilities

Composition capability rows use stable categories:

- `template_unavailable`;
- `transfer_syntax_unavailable`;
- `codec_unavailable`;
- `provider_unavailable`;
- `independent_validator_unavailable`; and
- `resource_envelope_unsupported`.

Each row names the logical instance, template, optional slot or transfer
syntax, requirement, reason code, and message. A requested primary instance
with an unavailable required capability fails the transactional run. Dry-run
resolution may report unavailable rows without materializing output.

## Reporting boundary

Composition reports project only composition entries, templates, SOP Classes,
content sources, transfer syntaxes, references, validation layers,
determinism, and unavailable capabilities. They never join entries to registry
profiles or add generated/planned/skipped case counts. A report reader must
select behavior from `run.kind`, not infer it from field presence.

## Publication record

The publication block records staging completion, validation completion,
expected entry count and bytes, final atomic-promotion status, and cleanup
status. A published manifest can only record all required internal validation
groups as passed. Failed and dry-run attempts are returned as command results,
not promoted as ordinary composition roots.
