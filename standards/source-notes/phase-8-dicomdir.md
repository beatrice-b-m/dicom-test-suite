# Phase 8 DICOMDIR Evidence

Verified: 2026-08-28

## Locked standard

The implementation target is DICOM 2026b, matching `standards.lock.json`.

- PS3.10 Section 8.6 requires exactly one `DICOMDIR` File ID in every
  conforming File-set, forbids references outside that File-set, requires
  Explicit VR Little Endian for the Media Storage Directory SOP Instance, and
  requires the Media Storage Directory Storage SOP Class in File Meta
  Information. The File Meta SOP Instance UID is the File-set UID.
  Source:
  <https://dicom.nema.org/medical/dicom/2026b/output/chtml/part10/sect_8.6.html>
- PS3.10 Section 8.2 limits File IDs to one through eight Components and each
  Component to one through eight characters from the restricted repertoire.
  The generator will use uppercase, extension-free Components and will not
  attach semantic meaning to their hierarchy.
  Source:
  <https://dicom.nema.org/medical/dicom/2026b/output/chtml/part10/sect_8.2.html>
- PS3.3 Section F.2 defines a strictly hierarchical Basic Directory. If the
  Directory Information Module is present, every DICOM File in the File-set is
  referenced and each File is directly referenced by at most one Directory
  Record.
  Source:
  <https://dicom.nema.org/medical/dicom/2026b/output/chtml/part03/sect_F.2.html>
- PS3.3 Section F.3 makes File-set Identification mandatory and defines the
  Directory Information Module and Directory Record Sequence used by the
  mixed-object fixture.
  Source:
  <https://dicom.nema.org/medical/dicom/2026b/output/chtml/part03/sect_F.3.html>

The registry's PS3.6 evidence already locks Media Storage Directory Storage UID
`1.2.840.10008.1.3.10` and Explicit VR Little Endian UID
`1.2.840.10008.1.2.1`.

## Provider and independent checks

The approved first provider is optional DCMTK `dcmmkdir` 3.7.0. Its general
purpose profile checks candidate files before creating a DICOMDIR and supports
a fixed File-set ID, explicit output path, strict required attributes, and
filename mapping. The provider executable, version, argument vector, and
SHA-256 must be recorded.

Provider output is not self-validating. Promotion requires all of the
following independent or structurally separate checks:

1. dicom3tools `dciodvfy -new` on the DICOMDIR;
2. dicom3tools `dcentvfy` across the File-set where supported;
3. the Rust validator's own closure walk over Directory Record references,
   File IDs, referenced file hashes and SOP identities; and
4. a second DCMTK parser check, reported as same-provider-family evidence, not
   as independent interoperability proof.

dcm4che remains the approved independent peer target. Its absence does not
justify calling DCMTK-versus-DCMTK independent; the capability must remain
explicitly qualified until the pinned peer is installed.

## Initial mixed File-set

The first File-set contains stable, synthetic representatives of three object
families generated by existing recipes:

- one image instance;
- one derived instance with a closed reference to its source; and
- one non-image instance.

All referenced files are copied into a private staging tree using conforming
File ID Components. The DICOMDIR and referenced files are promoted together
only after the provider exits successfully and every closure check passes.
Partial provider output and temporary backup files are never promoted.
